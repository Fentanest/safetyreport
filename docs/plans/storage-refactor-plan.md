## 1. 지금 구조의 핵심 문제 (요약)

1. **누가 어떤 열을 쓰는지 정해져 있지 않다.** 크롤러가 행 전체를 덮어써서(서버 `on_conflict_do_update` 전 열, 모바일 `REPLACE`) 사용자가 고친 값·별점 사유·수동 판단이 재크롤링 때 사라진다.
2. **NULL 과 '' 의 의미가 없다.** 변환·저장 곳곳에서 `or ""`, `?? ''`, `str(None)`="None" 이 섞인다. 변경 감지도 `str()` 비교라 가짜 변경이 생긴다.
3. **한 번의 논리적 저장이 여러 트랜잭션으로 쪼개져 있다.** detail → merge 재생성 → 중복군 재생성이 따로 커밋되고, 중간에 실패하면 화면(merge 기준)이 어긋난다.
4. **열 목록이 손으로 10곳 넘게 복제되어 있다**(서버 6곳, 모바일 15곳). 새 열(사진 촬영 시각)을 넣을 때마다 누락 위험이 생긴다.
5. **파괴적 작업에 보호가 없다.** 모바일 전체 재동기화·데모 로그인·백업 복원, 서버 `--reset`·서버 DB 복원이 백업/롤백 없이 지운다.

반증·보류: G-4(백업 내보내기가 WAL 을 잃는다) — SQLite 는 마지막 연결을 닫을 때 WAL 을 합친다(실험 확인). 실제 위험은 M-25. G-3(편집기가 별점 변경에 synced_at 을 안 올린다) — synced_at 은 "상세 내용 변경 시각"이라 설계상 맞다. 결함이 아니라 §4-3 의 규칙 정리 대상.

## 3. 목표 설계

### 3-1. 원칙
1. **열마다 주인이 있다.** 모든 열을 아래 4가지 중 하나로 분류하고, 쓰는 코드는 자기 열만 쓴다.
   - `site`(안전신문고가 원천: 처리상태·답변·첨부 등) — 크롤러만 쓴다.
   - `user`(사용자가 원천: 감시목록, 편집 수정값, 중복 판단, 로컬 별점 제출 기록) — 사용자 동작만 쓴다.
   - `derived`(계산값: 주소정규화·좌표·사진 촬영 시각·synced_at·처리상태 정규화·category) — 정해진 계산기만 쓴다.
   - `meta`(sync_meta, 스키마 버전 등).
2. **NULL = 모름/아직 안 해 봄, '' = 비어 있음이 확인됨.** 정규화는 파서 출력 한 곳에서만 하고, 저장·변환·API 는 값을 바꾸지 않는다.
3. **한 번의 논리적 저장 = 한 트랜잭션.** 신고 1건 저장은 title·detail·entry_value·raw·merge(그 ID)·변경기록을 한 트랜잭션에서 끝낸다. 네트워크는 트랜잭션 밖에서 미리 한다.
4. **열 목록은 한 곳(계약 파일)에서만 정의한다.** 서버·모바일 스키마, 변환기, API 직렬화, 편집기 필드가 모두 이 파일에서 나오거나 이 파일로 검사된다.
5. **지우는 작업은 먼저 새로 만들고 바꿔 끼운다**(stage → verify → swap, 백업 보관). 제자리 삭제 금지.

### 3-2. 공유 계약 파일
`contracts/storage-contract.json` 을 두 레포에 **바이트 동일**하게 둔다(과태료 검사 벡터와 같은 방식, 양쪽 테스트가 sha256 비교).
내용: 표 목록, 표별 열(이름, 타입, NULL 의미, 기본값, 주인, 교환 여부, 서버 표 이름 ↔ 모바일 표 이름 대응), 스키마 버전.
- 서버 테스트: SQLAlchemy 모델 ↔ 계약 일치, `restore_from_mobile_db`·`save_crawl_changes`·API 직렬화가 계약의 교환 열을 모두 다룸.
- 모바일 테스트: `_create` 결과 스키마 ↔ 계약 일치, `importFromServerDb` 가 교환 열을 모두 다룸, `Report` 매핑·`reportToChangeMap` 검사.
- 대안: 코드 생성(계약 → Python/Dart 소스). 처음에는 **검사만** 하고, 열 목록 복제 제거가 끝난 뒤 생성 여부를 다시 판단한다(빌드 도구 추가 부담 때문).
- 서버와 앱은 배포 시기가 달라 운영 중에는 계약 판이 어긋난다(G9-3). 그래서 바이트 동일 검사는 **함께 개발하는 짝 브랜치**에서만 강제하고, 운영 교환은 DB 에 기록된 `schema_version` 과 API 기능 목록으로 맞춘다. 각 쪽은 한 단계 이전 판(N-1)을 읽을 수 있어야 한다.

### 3-3. 서버 저장 계층
```
core/storage/
  contract.py        계약 파일 로드·검증
  schema.py          SQLAlchemy 표 정의(계약과 테스트로 일치 보장), 인덱스
  migrations/        번호 붙은 마이그레이션(PRAGMA user_version), 각 단계에 구버전 DB fixture 테스트
  records.py         CrawledTitle / CrawledDetail dataclass (튜플 입력 제거)
  change.py          계약 타입 기준 정규화 비교(NULL/''/0 구분 규칙 명시)
  reports_repo.py    save_crawled(records) — 열 주인 규칙대로 명시적 upsert, 건별 트랜잭션에 merge(해당 ID) 갱신 포함
  user_repo.py       감시목록·편집 수정값·별점 제출·중복 판단 저장
  change_log.py      변경 기록 테이블 + 기기별 읽은 위치
  exchange/          서버↔모바일 변환(계약 구동), stage→swap 복원
```
- 크롤링 저장은 상세를 받는 즉시 건별로 저장한다(S-9). 지오코딩·사진 시각은 저장 전에 미리 구하거나(캐시만) 저장 뒤 작업 큐로 채운다(S-7·S-8).
- merge 표는 **유지**하되 전체 재생성 대신 바뀐 ID 만 같은 트랜잭션에서 갱신한다(권장안, 결정 D-4). `clear_old_attachments` 는 merge 쓰기가 아니라 조회 시 규칙으로 옮긴다(S-31).
- merge 는 **"화면에 보이는 최종값"** 이다: `merge = title + detail(사이트 원본) + override(사용자 수정값)`. 수정값은 merge 갱신 때 덮어 넣으므로 통계·내보내기·API·모바일 가져오기는 지금처럼 merge 만 읽으면 된다(G9-3 의 "모든 조회에 JOIN 필요" 우려 해소).
- 중복군은 본문(raw_content) sha256 완전 일치로 묶는다(`duplicate_group_service.py:93`, 거리 기준 아님). 신고 1건 저장 때는 그 신고의 이전 해시·새 해시 그룹만 같은 트랜잭션에서 다시 계산한다. 전체 재생성은 마이그레이션·수동 버튼에서만.
- `upgrade_schema` 는 서버 시작 시 한 번, 버전이 바뀔 때만 무거운 작업을 한다(S-22). 크롤링 서브프로세스는 버전만 확인한다.

### 3-4. 모바일 저장 계층
```
lib/storage/
  storage_contract.dart   계약 파일(assets) 로드·검증
  schema.dart / migrations.dart   단일 버전 정의, "이미 있는 열" 외 오류는 실패로 처리(M-15·M-26)
  report_repository.dart  upsertCrawled — 명시적 열 갱신(REPLACE 금지), 기존 행 1회 읽기
  user_repository.dart    감시목록(단일 원천)·별점·편집 수정값·중복 판단
  change_events.dart      쓰기 후 캐시 무효화 알림(M-4·M-5)
  exchange/               서버 DB 가져오기·백업 복원 모두 stage→swap(M-11)
```
- UPSERT 문법(`ON CONFLICT DO UPDATE`)은 SQLite 3.24 이상이 필요하다. 앱은 Android 기본 SQLite 를 쓰고 minSdk 가 Flutter 기본값이라 구형 기기에서 없을 수 있다 → **UPDATE 후 없으면 INSERT** 방식으로 구현한다(버전 무관). 대량 저장은 `batch` 로 묶어 왕복을 줄인다(G9-3).
- 모바일 `reports` 는 **사이트 원본**을 담는다(서버 title+detail 과 같은 뜻). 사용자 수정값(`report_override`)과 6개월 첨부 가림은 화면에 보일 때 적용한다.
  (2026-09-24 R2 에서 정정: 처음엔 reports 에 수정값을 덮어 넣으려 했으나, 그러면 모바일→서버 복원 때 서버 상세 원본이 수정값·"6개월 초과"로 바뀐다 — 왕복 검사가 32건으로 잡아냄.
  교환은 원본 + 수정값 표로만 한다. 서버 가져오기는 merge 가 아니라 title+detail 을 읽는다.)
- 전체 재동기화는 새 DB 를 만들어 채운 뒤 바꿔 끼우고, 사용자 소유 데이터(감시목록·중복 판단·편집 수정값·지오코딩 캐시)는 옮겨 담는다(M-1).
- 데모 계정은 별도 DB 파일을 쓴다(M-24, 결정 D-7).

### 3-5. 사용자 소유 데이터
| 데이터 | 단일 원천(목표) | 지금 |
|---|---|---|
| 감시목록 | 서버 `mysafety_watchlist` / 모바일 `sync_meta.watchlist` → 교환 시 한 표로 통일 검토 | 서버 표 + sync_meta 사본 + merge 열 + 모바일 열 + 메모리(5곳) |
| 편집 수정값 | 새 표 `report_override(ID, 열, 값, 수정 시각)` — 조회 시 원본 위에 덮어 보여 줌, 재크롤링이 지우지 않음 | detail/merge 원본을 직접 수정 → 재크롤링이 되돌림 |
| 중복 판단 | 새 표 `duplicate_decision(안정 키, 상태, 대표건, 메모)` — 재생성은 멤버만 다시 계산 | 그룹 표에 섞여 있어 재생성·reset 에 소실 |
| 별점 | 사이트 값이 있으면 사이트 값, 비었거나 조회 실패면 기존 값 유지. 로컬 제출은 "제출함(사이트 확인 전)"으로 기록 | 재조회가 덮음(M-2·M-3), 서버 일괄 별점은 점수 미저장(S-25) |

새 표도 교환 대상이다(§3-1). 계약 파일에 넣고 왕복 검사를 확장한다.

### 3-6. 증분과 알림
- 변경 감지는 계약 타입 기준 정규화 비교(S-5). 변경으로 치는 열 목록을 계약에 적는다(서버·모바일 같게, S-6).
- 변경 기록은 DB 표(`change_log`)에 쌓고, `/api/v1/crawl/results` 는 기기별 읽은 위치로 응답한다(S-18). 응답 형식은 그대로 유지한다(결정 D-5).
  - 구버전 앱은 기기 식별자를 보내지 않는다(G9-3). 식별자 없는 요청은 공용 "legacy" 위치 하나를 함께 쓴다 → 지금과 같은 동작이라 나빠지지 않는다. 새 앱은 기기 식별자를 보내 자기 위치를 갖는다.
  - 신앱 ↔ 구서버: 신앱은 `/server/version` 의 기능 목록으로 새 방식 지원 여부를 확인하고, 없으면 지금 방식으로 동작한다.
- 재크롤링 대상: 종결여부 NULL 포함, 빈 DB 판정에 주정차 포함(S-19).

### 3-7. 교환(서버↔모바일)
- DB 파일 경로와 API 경로가 같은 값을 보내게 한다(S-35): API 직렬화도 NULL 을 null 로, 정수는 정수로.
- 복원은 서버·모바일 모두 임시 DB 로 변환 → 무결성 검사 → 크롤링 중이면 거부 → 백업 보관 → 바꿔 끼우기(S-28·M-11).
- 스키마 버전을 sync_meta 에 기록. 가져올 때 구버전은 마이그레이션, 신버전은 "앱/서버 업데이트 필요"로 거부.
- 버전 혼재 기간: 새 표·열은 **추가만** 한다. 구버전 앱은 모르는 표를 무시하므로 구앱↔신서버 교환이 깨지지 않는다. 이를 왕복 검사에 "구버전 상대" 경우로 넣는다.
