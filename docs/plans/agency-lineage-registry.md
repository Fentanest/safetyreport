# 기관·행정구역 코드 이력으로 기관별 통계를 일원화하는 계획

작성: 2026-09-28. 설계 검토 단계이며 제품 코드와 DB 스키마는 아직 변경하지 않았다. 전제: 안전신문고의 최신 답변에서 `C_MANAGE_ORG`와 `C_MANAGE_ORG_NAME`을 함께 저장한다. [기존 지역코드 조사](agency-normalization-code-history.md)와 [2014년 이후 법정동 코드 목록](../reference/administrative-region-codes-2014.md)을 이어받는다.

## 결론

**원본 기관코드와 기관명은 신고의 사실로 보존하고, 통계용 기관 ID는 버전이 붙은 기관 이력표에서 계산한다.** 기관코드가 그대로인 개명은 그 코드 하나로 묶인다. 코드가 재발급된 개명·소속 변경은 옛/새 코드로 갈라지므로 `이전기관코드`를 따라 같은 통계 키로 묶는다. 광주동부경찰서가 실제 사례다. 지역코드 이력은 처리기관의 소속 지역을 정하는 별도의 축으로 쓴다.

커뮤니티 맵 저장소가 공식 자료를 받아 **버전 고정된 공개 코드 이력 자료**를 만들고 배포하는 방식을 권장한다. PC 서버·모바일 Client·Standalone은 같은 버전의 자료를 내려받아 로컬에서 해결한다. 커뮤니티 맵의 수집·공개 통계도 그 자료로 계산한다. 신고마다 외부 API를 호출하면 오프라인 Standalone이 동작하지 않고, 개인 신고의 기관·답변일이 별도 서버로 전송되므로 채택하지 않는다. 온라인 `resolve` API는 대조·진단용으로만 둔다.

## 확인된 근거와 한계

- [공식 기관코드 조회](https://www.code.go.kr/stdcode/orgCodeL.do)는 7자리 영숫자 코드, 전체기관명, 차상위기관코드, 대표기관코드, 생성·폐지일, 존폐여부, `이전기관코드`를 제공한다. 2026-09-28 전체 자료와 로컬 안전신문고 API 원본 4쌍의 코드·전체기관명을 대조해 모두 일치했다.
- 실제 광주동부경찰서는 `1812314`(광주광역시경찰청, 2026-06-30 폐지) → `1815198`(광주경찰청, 2026-07-01 생성)이고 새 코드의 `이전기관코드`가 옛 코드를 가리킨다. 따라서 **같은 기관도 코드가 바뀐다.**
- 공식 전체 자료 472,175개 코드 중 `이전기관코드`가 채워진 행은 36,567개다. 293개 연결은 이전 코드가 현재 전체 자료에 없고, 989개 이전 코드에는 후속 코드가 둘 이상 있다. 이 수치에는 국·과·팀 등 하위 조직이 포함된다. 기관 단위로 잘라도 누락·분할은 별도 처리해야 한다.
- 국가보훈처 `1180439`와 국가보훈부 `1830104` 전남서부보훈지청은 이름·시점으로 후계 후보가 보이지만 새 코드의 `이전기관코드`가 비어 있다. **이번 범위에서는 코드 외의 추정으로 연결하지 않고 별개 기관으로 둔다.**
- [공식 법정동 코드 목록](https://www.code.go.kr/stdcode/regCodeL.do)은 지역 이름·상위 코드·생성·폐지일을 주지만 일반적인 `이전지역코드` 연결은 주지 않는다. [코드변경 안내](https://www.code.go.kr/bbsmng/dataBbsL.do)의 개편 자료를 별도 사건으로 읽어야 한다. 현재 스냅샷만으로 2014년부터 같은 코드에 붙었던 모든 과거 이름을 복원할 수도 없다.
- 가져온 모바일 DB의 신고 6,208건에는 기관코드 열이 없다. 기존 6,031건의 지자체·경찰 신고는 기관명으로 후보를 만들 수 있지만, 옛 신고에 코드가 있었던 것처럼 표시하지 않는다.

## 데이터 의미와 저장

| 값 | 의미·저장 원칙 |
| --- | --- |
| `처리기관` | 안전신문고의 전체 기관명 원문. 현재처럼 보존한다. |
| `처리기관코드` | `answers[].C_MANAGE_ORG` 원문. 7자리 **TEXT**, `B410002` 같은 영문 코드와 앞자리 0을 보존. 답변·코드가 없으면 `NULL`. 최신 답변 선택 규칙은 기존 파서와 동일. |
| `답변일` | 그 답변과 코드의 시점을 확인하는 날짜. 신고일·동기화일로 대신하지 않는다. |
| `기관소속지역코드` | 기관 이력표에서 계산한 처리기관 소속 행정구역. 지역→기관→담당자 통계의 첫 단계. 원본 신고 필드가 아닌 버전별 파생값. |
| `위반지역코드` | 별도 지역 통계에만 쓰는 선택 항목. 출처가 있는 원본 코드 또는 주소·좌표에서 도출한 코드임을 구분한다. 기관 소속 지역과 섞지 않는다. |
| `institution_id` | 기관 계보표가 부여하는 불변 내부 ID. 원본이 아닌 파생값이며 `registry_version`과 함께 계산·캐시한다. |

서버는 detail·merge 테이블과 `/api/v1` 응답에 기관코드를 추가하고, 모바일은 `Report`·Standalone 파서·SQLite `reports`·Client 역직렬화에 추가한다. 서버↔모바일 양방향 DB 교환과 구버전 백업 업그레이드는 같은 작업에서 바꾼다. 새 필드의 `NULL`/빈 문자열, 영문 코드, 앞자리 0을 보존하고 전체 컬럼 왕복을 검사한다(`PROJECT_RULES.md` §3-1). 기존 DB는 이름·답변일로 별도 역매칭하되 확정되지 않으면 코드 공란을 유지한다. 원본 `처리기관`을 정규화 이름으로 덮어쓰지 않는다.

## 버전 관리 코드 이력의 구조

1. **원본 노드**: 기관코드, 전체/최하위 이름, 차상위기관코드, 이전기관코드, 기관유형, 생성·폐지일, 원본 파일 SHA-256, 수집 시각. 지역코드는 10자리 문자열, 이름, 상위 코드, 생성·폐지일, 출처를 별도 노드로 둔다. 여러 시점의 공식 스냅샷을 보존해 같은 코드의 이름 변경도 감지한다.
2. **변경 사건**: 기관은 공식 `이전기관코드`를 직접 읽는다. 한 이전 코드에 후속 기관 단위 코드가 정확히 하나인 1:1 연결만 같은 통계 키로 자동 확정한다. 이전기관코드가 비면 새 기관 ID를 부여하며 수동·이름 추정으로 이어 붙이지 않는다. 1:다 분기는 자동 통합하지 않는다. 지역은 이전 코드 필드가 없으므로 별도의 `from_code`, `to_code`, 시행일, 개편 유형, 공식 근거가 있는 변경 사건을 관리한다.
3. **기관 경계**: 조직 트리의 코드에서 부모를 올라가 시·군·구, 경찰서, 소방서, 지방청·지청, 공기업 본사 등 집계할 행정기관을 고른다. 국·과·팀·지구대는 상위 기관에 속한다. `대표기관코드`를 곧장 통계 키로 쓰지 않는다(경찰서 여러 곳이 경찰청 대표 코드로 합쳐질 수 있다).
4. **기관 ID**: 최초 등록된 기관 단위 코드에 불변 `institution_id`를 부여하고, 확인된 1:1 이전기관 연결의 새 코드가 이를 승계한다. 코드가 바뀌어도 앱에 기관별 대응표를 손으로 추가하지 않는다. 최신 표시 이름은 유효한 코드의 이름에서 가져오고, 상세에는 신고 당시 이름을 보인다. 이전기관코드 공란 또는 기관 단위 1:다 분기는 각각 새 ID로 둔다.
5. **기관 소속 지역**: 기관마다 시점별 소속 법정동 지역코드를 연결한다. 지자체는 해당 시·군·구/시·도, 경찰·소방은 확인된 조직 소속 지역 수준, 전국 기관은 `전국`, 소속 지역을 판정할 수 없는 기관은 `지역 미확인`으로 둔다. 기관의 우편 소재지나 이름 속 지역을 관할 범위로 간주하지 않는다. 시군구 수준 소속이 없는 기관을 이름만으로 구까지 내려놓지 않는다.

### 자동 해결 순서

```text
답변 기관코드 + 원문 이름 + 답변일
  → 기관코드 원본 노드 확인(이름·유효기간 불일치는 경고로 기록)
  → 차상위기관코드를 따라 기관 경계까지 올림
  → 1:1 이전기관코드 연쇄를 따라 institution_id 결정
  → 기관 소속 지역의 시점별 코드와 지역 변경 사건을 대조
  → {current_region_key, institution_id, 표시명, 당시명, 상태, registry_version}
```

코드가 없는 옛 신고는 이름+답변일+상위 경로가 **유일하게** 맞을 때만 특정 공식 코드의 신고로 역매칭할 수 있다. 이 작업은 누락된 `이전기관코드`를 만들어 내는 것이 아니다. 이름과 코드가 충돌하거나 날짜가 경계에 걸리면 `candidate`/`unresolved`로 보존하고 자동 확정하지 않는다. 미해결 건도 신고 총수에서 빠지지 않으며 기관별 표에는 원문 이름의 별도 행 또는 명확한 미확인 행으로 표시한다.

기관코드의 **1:다 분기**는 이전 코드가 있다는 이유로 후속 기관 둘을 하나로 묶지 않는다. 하위 국·과·팀의 분기라면 먼저 기관 경계로 올려 같은 상위 기관에 속하는지 확인한다. 기관 자체가 분기했다면 옛 기관과 새 기관을 각각 유지한다. `이전기관코드`가 하나뿐인 자료에서 다:1 기관 통합의 모든 전임 기관을 코드만으로 확정할 수도 없으므로, 연결되지 않은 쪽은 별개로 둔다.

### 지역 → 기관 → 담당자

첫 단계의 지역은 사용자가 정한 대로 **신고 발생지가 아닌 처리기관 소속 행정구역**이다. 집계 행은 `(현재 지역 키, institution_id, 담당자)` 순서로 내려간다. 시군구 소속 기관은 그 시군구와 상위 시도에 한 번씩 반영하고, 시도 소속 기관은 시도에만 둔다. 전국 기관·지역 미확인은 별도 최상위 묶음이다. 담당자 집계와 필터도 같은 기관 ID를 사용한다.

커뮤니티 맵의 기존 `region_code` 필터와 지도는 **신고 발생지** 기준이다. 이를 기관 소속 지역으로 바꾸면 현재 지도·지역 통계의 의미가 깨지므로, 새 위계에는 `agency_region_key`를 별도로 두고 API 필터도 구분한다. 지역별 신고 지도와 기관 소속 지역별 표를 같은 값으로 표시하지 않는다.

- **지역 개명·이관 1:1**: 옛 지역코드와 새 지역코드를 하나의 현행 지역 키에 연결한다. 해당 기관 ID는 기관코드의 1:1 연쇄를 따로 따라간다.
- **지역 통합 다:1**: 옛 지역 A·B를 새 지역 C의 현행 키 아래 집계한다. 이는 소속 지역의 합산이며 A·B의 서로 다른 기관까지 한 기관으로 합치지는 않는다.
- **지역 분할 1:다**: 분할 전 기관의 옛 신고는 처리기관 소속 지역이 A였다는 사실만 있다. 따라서 B·C 중 한 곳에 임의 배정하지 않고 공통 상위 지역 밑의 `분할 전 A`에 한 번만 둔다. 상위 지역까지 분할됐다면 `분할 전 지역`을 전국 아래 둔다. 새 기관 B·C의 신고는 각각 새 지역에 둔다. 신고 위치로 옛 신고를 나누면 **기관 소속 지역**이 아니라 **현재 위반 장소** 기준이 되므로 이 통계에는 쓰지 않는다.

지역 변경 사건은 [공식 코드변경 안내](https://www.code.go.kr/bbsmng/dataBbsL.do)와 지역코드 생성·폐지일을 근거로 이력 자료에 추가해야 한다. 같은 코드가 유지되는 이름 변경과 명확한 1:1 이관은 스냅샷 diff로 후보를 자동 생성할 수 있지만, 지역코드에는 기관코드의 `이전기관코드` 같은 연결이 없어 통합·분할을 매번 자동 **확정**할 수는 없다. 코드에 개별 `if`를 추가하지 않고 검증된 변경 사건 데이터로 관리한다.

## 자료 갱신과 배포

1. 커뮤니티 맵 저장소의 별도 빌더가 공식 기관·법정동 **전체 자료**를 주기적으로 내려받고 원본 SHA-256·수집 시각을 기록한다. 기존 데이터가 지워졌거나 코드 재사용·중복·부모 순환·날짜 역전·참조 대상이 없는 이전기관코드·분기가 있으면 검증을 중단하거나 미연결 상태로 기록한다. 이전기관코드가 단순히 빈 기관은 새 ID로 둔다. 공식 변경 공지를 지역 변경 사건의 근거로 수집한다.
2. 직전 버전과 diff를 만들어 같은 코드의 이름 수정, 신규·폐지 코드, 1:1 이전기관 연결, 지역 경계 변경을 분류한다. 기관코드 1:1 연쇄만 같은 기관 ID를 자동 승계한다. 기관코드의 공란·기관 단위 분기는 별개 ID로 두고 이름으로 임의 보정하지 않는다. 사람이 추가하는 대응은 **지역 변경**에 한해 `코드쌍 + 시행일 + 공식 근거 + 변경 유형` 데이터에 둔다. 앱 코드의 문자열 치환 규칙에 누적하지 않는다.
3. 검증된 이력에서 `manifest(version, published_at, source_hashes, schema_version, content_hash)`와 **압축된 조회용 스냅샷**을 생성한다. 런타임은 47만 개 원본 행을 직접 순회하지 않는다. 사전 계산된 `기관코드 → 기관경계 → institution_id`, 이름·기간 별칭, 지역 변경 사건을 인덱스로 사용한다. 실제 파일 크기를 측정해 필요하면 접두어별 분할·증분 업데이트를 적용한다.
4. PC·모바일은 마지막으로 검증된 버전을 원자적으로 교체하고 실패 시 기존 버전을 유지한다. Standalone 설치본에도 작동 가능한 기준 버전을 넣는다. 통계·CSV·필터·드릴다운은 **한 요청에서 같은 registry_version**을 사용한다. 버전 갱신 시 파생 키 캐시를 다시 계산하고 이전 집계와 변경 건수를 기록한다.

### 커뮤니티 맵 연동

- 현재 커뮤니티 맵은 `agency_name`의 해시(`a1:...`)를 `agency_key`로 저장하므로 개명 시 분리된다(`server/ingest/observation.ts`). 서버측 resolver가 같은 버전의 이력표에서 **기관 ID 기반 키**를 만들도록 바꾼다. 클라이언트가 보낸 정규화 키는 신뢰하지 않는다.
- 업로드 계약은 기관코드를 포함하는 새 버전으로 확장한다. 현행 observation-v2는 `additionalProperties: false`이고 서명 대상이므로 필드만 끼워 넣지 않는다. 먼저 커뮤니티 맵이 구버전·신버전을 함께 받아들이고, 그 다음 PC·모바일이 새 버전을 보낸다. 공유 동의·공개 필드 계약도 함께 확인한다.
- 기존 private fact의 원문 기관명·답변일로 재투영하고, 기관코드가 없어서 모호한 과거 행은 별도 상태로 남긴다. 기관코드가 있는 클라이언트의 재공유를 통해 보강할 수 있으나 재업로드를 강제하지 않는다. `agency_key` 필터, 담당자 키, 공개 기관표·개인 비교를 같은 버전으로 재집계한다. API 응답에는 `registry_version`과 미해결 건수를 포함한다. 기존 `a1:` URL/북마크는 확인된 alias만 새 키로 이동시킨다.
- 공개 읽기 경로에는 버전·스냅샷 다운로드 및 코드/이름/날짜만 받는 배치 대조 API를 둘 수 있다. 개인 신고번호·주소·본문을 정규화 API에 보내지 않는다. 통계 요청마다 대조 API가 호출되도록 설계하지 않는다.

## 적용 순서와 완료 기준

1. **의미 고정**: 기관코드 1:1 승계·공란 분리·1:다 분기, 처리기관 소속 지역의 통합·분할 표기, `confirmed/candidate/unresolved` 기준을 fixture로 합의한다. 개인 신고 통계와 커뮤니티 전국 통계의 모집단은 계속 별개다.
2. **이력 빌더**: 공식 자료 재수집·diff·검증·스냅샷 생성. 광주동부경찰서 1:1 연결, 보훈지청 이전 코드 공란의 별개 ID, 공기업 영문 코드, 지역 다:1 통합·1:다 분할을 고정 fixture로 검증한다.
3. **원본 코드 보존**: 서버/모바일 파서·스키마·API·DB 교환을 한 단위로 변경한다. 서버→모바일→서버와 모바일→서버→모바일 왕복에서 모든 컬럼과 `NULL`/빈 문자열을 비교한다. 구버전 DB 복원도 검사한다.
4. **읽기 전용 그림자 집계**: 가져온 DB와 합성 fixture에서 현재 기관표와 새 기관표를 나란히 계산해 병합·분리·미해결 수를 기록한다. 6,208건을 원본 수정 없이 조사하며 코드 없는 기존 건의 자동 확정 비율을 과장하지 않는다.
5. **제품 집계와 커뮤니티 맵**: 웹·모바일 Client·Standalone의 지역→기관→담당자 통계, 필터, CSV, 상세 이동을 같은 지역 키·기관 ID로 전환한다. 현재의 `agencyExact` 원문 이름 필터와 `경찰` 문자열 포함 여부는 각각 기관 ID 필터와 기관 유형 필터로 대체해 옛 이름도 상세에서 빠지지 않게 한다. 커뮤니티 맵은 원본 fact를 유지하며 전체 이력 버전으로 재집계한다. 버전 변경 전후에 전체 신고 수, 분류·상태·금액 합계가 같고 기관별 이동 건수 합이 맞는지 검사한다.
6. **운영**: 공식 자료 갱신 감지, 검토 대기 사건, 마지막 성공 버전, 원본 출처와 실패 사유를 모니터링한다. 공지 없이 자동 확정된 새 1:다/다:1 연결은 배포하지 않는다.

완료 판정에는 서버/모바일 동일 입력→동일 `institution_id`·표시 이름·상태의 공용 벡터, 오프라인 버전 고정, DB 양방향 왕복, 커뮤니티 맵 기존/새 업로드 호환과 재집계, 웹·모바일 표/필터/드릴다운의 동일 합계를 포함한다. 구현 전 계획 문서이므로 이 검증들은 아직 실행되지 않았다.
